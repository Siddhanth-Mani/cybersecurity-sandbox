Reconnaissance & Information Gathering

The first phase of any security assessment. Professionals map out systems, services, domains, and technologies to understand the attack surface before active testing begins.

🌐
Passive Recon
Gathering information without directly interacting with the target. Uses OSINT, WHOIS, DNS records, certificate transparency logs, and public repositories.
🔍
Active Recon
Direct interaction with target systems via port scanning, service fingerprinting, web crawling, and directory enumeration. Leaves traces in server logs.
🗺️
Attack Surface Mapping
Identifying all entry points: exposed ports, APIs, subdomains, third-party integrations, and open S3 buckets or cloud storage.
Common Recon Commands
# Full port scan with service detection and defaults
nmap -sV -sC -p- target.com

# Subdomain enumeration + probing live status
subfinder -d target.com | httpx

# Certificate Transparency Log subdomain enumeration
curl -s "https://crt.sh/?q=%.target.com&output=json" | jq .[].name_value

# Query DNS records in short format
dig +short ANY target.com

Server-Side Request Forgery (SSRF)

Occurs when an application fetches resources based on user-supplied input without sufficient validation, potentially exposing internal services unreachable from the internet.

Attack VectorRiskDescription
Internal Metadata Access Critical Fetching cloud metadata endpoints (169.254.169.254) to retrieve IAM credentials and instance data.
Port Scanning via SSRF High Using the server as a proxy to scan internal network ports and services not exposed externally.
Protocol Abuse High Leveraging file://, dict://, gopher:// schemes to exfiltrate data or interact with internal services.
Blind SSRF Medium No response visible but out-of-band callbacks confirm SSRF via DNS or HTTP to a controlled server.
Defensive Controls
URL allowlisting Network segmentation Disable internal redirects Block private IP ranges IMDSv2 enforcement

Authentication & Authorization

Authentication verifies identity; authorization controls access. Weak implementations lead to account takeovers, privilege escalation, and sensitive data exposure.

🔑
Broken Authentication
Weak passwords, missing MFA, session fixation, insecure token storage, and predictable session IDs allowing account takeover.
🚪
Broken Access Control
IDOR, path traversal, missing function-level access checks, and CORS misconfigurations enabling unauthorized resource access.
⬆️
Privilege Escalation
Horizontal escalation (accessing other users' data) or vertical escalation (gaining admin access from a standard account).
🎫
JWT Vulnerabilities
Algorithm confusion (RS256→HS256), weak secrets, missing signature validation, and the "none" algorithm attack.
Defensive Controls
Strong session management MFA enforcement RBAC / ABAC Secure JWT libraries Rate limiting Account lockout

Injection Vulnerabilities

Arise when applications pass untrusted data to interpreters without proper sanitization. One of the most critical and widespread vulnerability classes.

TypeSeverityDescription
SQL Injection Critical Manipulating database queries to bypass auth, extract data, or execute OS commands (via xp_cmdshell, INTO OUTFILE, etc.).
Command Injection Critical Injecting OS commands via shell metacharacters (;, |, &&, $()) when user input is passed to system functions.
SSTI Critical Server-Side Template Injection — exploiting template engines (Jinja2, Twig) to achieve RCE via crafted payloads like {{7*7}}.
XXE High XML External Entity injection to read local files, perform SSRF, or DoS via entity expansion attacks (Billion Laughs).
LDAP / XPath Injection High Manipulating directory or XML queries to bypass authentication or extract sensitive directory information.
Defensive Controls
Parameterized queries Input validation & encoding Least-privilege DB accounts Disable external XML entities Secure coding training

HTTP Request Smuggling

Exploits inconsistencies in how front-end and back-end servers parse HTTP request boundaries, leading to request queue poisoning and security bypass.

🔀
CL.TE Smuggling
Front-end uses Content-Length; back-end uses Transfer-Encoding. Attacker's smuggled prefix is prepended to the next user's request.
⚡
TE.CL Smuggling
Front-end uses Transfer-Encoding; back-end uses Content-Length. Reversed trust boundary allows similar poisoning effects.
🎯
Impact Scenarios
Bypass access controls, poison web caches, capture credentials in next victim's request, XSS via reflected content, and account hijacking.
Defensive Controls
End-to-end HTTP/2 Reject ambiguous requests Normalize traffic at edge Consistent server parsing Disable keepalive to backend
Request Framing Inspector Detect body delimiters

Web Application Firewalls

WAFs filter and monitor HTTP traffic between clients and web applications, detecting and blocking common attack patterns before they reach backend systems.

WAF Bypass TechniqueRiskDescription
Encoding Tricks High Double URL encoding, Unicode normalization, HTML entity encoding to evade signature-based detection.
Case Variation Medium Mixed case keywords (SeLeCt, uNiOn) to bypass case-sensitive pattern matching rules.
Comment Insertion High SQL comments (/**/) between keywords to break up recognized patterns while preserving query logic.
Header Manipulation High Forged X-Forwarded-For, X-Real-IP headers to spoof trusted IPs and bypass IP-based restrictions.
Chunked Transfer Medium Splitting payloads across chunked encoding segments to evade body inspection rules.
WAF Best Practices
Positive security model Regular rule updates Log & alert tuning Defense-in-depth OWASP Core Rule Set Rate limiting

Quick Reference & General Principles

Layered software security requires solid architecture rules. These core tenets define resilient software protection strategies.

PrincipleDetails
Defense-in-DepthNo single control is sufficient. Layer WAF, input validation, parameterized queries, least privilege, and monitoring. A bypass of one layer should not mean full compromise.
Least PrivilegeDatabase accounts, API keys, and IAM roles should have only the permissions they need. Reduces blast radius of injection and SSRF vulnerabilities.
Secure-by-DefaultFrameworks and libraries should ship with safe defaults. Developers should opt-in to dangerous features (e.g., raw queries, external entity parsing), not opt-out.
Zero Trust ArchitectureNever trust the network location. Authenticate and authorize every request, even internal service-to-service calls. Limits SSRF and lateral movement impact.
Logging & MonitoringLog authentication events, access control failures, and validation errors. Set up alerts for anomalous patterns. Detection is as important as prevention.
Patch & UpdateMost critical vulnerabilities exploit known, patched weaknesses. Maintain an SLA for applying security patches to frameworks, libraries, and server software.
